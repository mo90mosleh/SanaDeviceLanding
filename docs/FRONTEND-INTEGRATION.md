# Consultation delivery and GitHub Pages

The homepage and all five product pages share `Consultation`. Each collects full name, laboratory name and an Iranian mobile number. At mobile widths (up to 640px), the inline section is removed and all consultation CTAs open a native modal dialog. The fixed bottom bar is available on the homepage and product pages, with consultation and telephone actions. Product cards use authentic images: all five devices on the homepage, or the current family on a product page with its device preselected. Mobile users may change the selected device within that family. Desktop retains the inline form and existing homepage dropdown. Closing a form preserves the draft; opening it does not automatically summon the keyboard.

Name and laboratory inputs are both limited to 100 characters without visible counters. Phone input accepts ASCII digits only, a `09` prefix and 11 digits. An incomplete `0` is allowed while typing the prefix; submission still requires the complete number. Persian/Arabic digits in typing or paste open a clear keyboard-language warning without converting or accepting them. Spaces, letters, punctuation, international prefixes and alternative initial digits are rejected. Validation enforces the same complete-number rule.

Every form contains an offscreen, accessibility-hidden, non-tabbable website honeypot. Its value is sent as top-level JSON `honeypot` (normally `""`), including nonempty values so the owner can filter them in n8n. Add an IF condition before downstream actions: `{{ $json.body.honeypot }}` is empty (or `$json.honeypot` after unwrapping the body). Only the empty branch should continue to Google Sheets and notifications. This frontend change does not edit or activate the n8n workflow.

Following the owner's explicit choice, the browser sends JSON directly to the n8n production webhook. Its URL is deliberately public in the client bundle. No backend proxy or Render deployment is required. `VITE_CONSULTATION_API_URL` optionally overrides the public destination at build time; it is not a secret variable. The endpoint must permit CORS from `https://mo90mosleh.github.io`, including OPTIONS, POST and Content-Type.

The transport matches the verified `Sheet1` header row in the owner-confirmed CBC-BRO spreadsheet. Alongside the existing internal payload it sends `fullName`, `labName`, `mobile`, `product`, `company`, `pageUrl`, `campaign`, `source`, `medium`, `content`, `term`, and `time`. Laboratory name comes from `organization`, product from `productModel`, company from `manufacturer`, and the five attribution columns from the corresponding UTM keys. `pageUrl` includes only the actual page origin/path; arbitrary URL parameters are not forwarded in it. `time` is the client submission time in ISO UTC. Missing campaign parameters remain empty. Existing delivery aliases and destinations are preserved; `honeypot` is additive.

Payload keys remain `name`, `organization`, `mobile`, `productModel`, `manufacturer`, `productCategory`, `landingPage`, and `utm`. `landingPage` is `/` for homepage requests and the existing product route for device pages. Phone validation follows the ASCII-only rule above; five-key attribution behavior is preserved. Personal contact fields are not written to browser storage.

Only a successful HTTP acknowledgement displays “اطلاعات با موفقیت ثبت شد.” in a native modal dialog and clears all fields, including the homepage selector. The dialog has a visible confirmation button, a close button, Escape dismissal, focus containment/restoration and background scroll locking. The previous inline success ribbon has been removed; errors remain inline and preserve the inputs. A successful n8n response can be plain text or JSON. Failure or a twenty-second timeout preserves input and shows an error. Pending controls are disabled, duplicate submission is blocked, and no automatic retries are performed. HTTP acknowledgement does not establish whether subsequent n8n steps completed.

## Static publication

`github-pages.yml` builds the existing TanStack Start application with its repository base path, exports its six server-rendered pages and authentic public assets, and reviews them on a plain static HTTP server before uploading a Pages artifact. Nested product URLs have real `index.html` files, so refreshes work without a server fallback. Product content, specifications, routes and SEO metadata remain intact. The repository's Pages source must be GitHub Actions; first-time enablement may require an administrator to select this in Settings → Pages.

Regular tests intercept the public endpoint and send no customer/test lead to n8n. Browser checks cover homepage/device payloads, ASCII-only input, Persian/Arabic warnings, 09 prefix, 100-character bounds, honeypot forwarding, pending/duplicate handling, errors, retry and acknowledged clearing. A separate read-only OPTIONS probe verifies the real CORS preflight. The `Verify live consultation delivery` workflow sends exactly one clearly labelled synthetic record only on manual dispatch or an explicit `[verify-webhook]` commit. That check verifies the published homepage, HTTP acknowledgement and cleared fields without claiming downstream workflow completion.

## Brand and product family colors

The homepage uses the SANA logo red token `#bf0115` for its general actions and consultation form. CBC/Getein detail pages, family panels, device options and slideshow states use green `#02753b`; POCT/Wondfo equivalents use SANA logo blue `#0047bf`. The two family selectors in the homepage header retain their green/blue labels. Product-page specification links, model badges, workflow markers and focus states use the page's own color. Authentic manufacturer logos sit beside model titles and retain their original colors.

The consultation transport, validation, honeypot and submission behavior are unchanged by these visual refinements.
